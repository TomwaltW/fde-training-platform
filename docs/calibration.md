# 裁判标定

对应方案 3.4.4(标定流程)和 3.4.2 第 5、6 条(两道门槛)。上线前必须做一次;之后每次改评分规则、裁判提示词或换裁判模型,都要回归。

| 门槛 | 怎么算 | 过线 |
|---|---|---|
| 稳定性 | 同一份对话让裁判跑 N 次(默认 3),每次都用引擎校验、算分,看总分的极差 | 每个用例 max − min ≤ 6(即 ±3) |
| 一致性 | 每个维度的满分等分成 5 档(第 0–4 档),比较人工分和裁判分落在第几档 | 所有用例 × 7 个维度里,相差不超过 1 档的比例 ≥ 80% |

分数一律由引擎算(`checkJudgeOutput` + `scoreSession`),标定工具不另写算分逻辑。所以这里比的不是"裁判模型给的分",而是"裁判抽出的证据 + 代码规则"最终算出的分,和线上复盘看到的完全一致。

档位举例:D1 满分 20,每 4 分一档,`[0,4)` 第 0 档、`[4,8)` 第 1 档……`[16,20]` 第 4 档。人工 16(第 4 档)和裁判 12(第 3 档)算一致;人工 16 和裁判 11.9(第 2 档)不算。

## 1. 标定用例长什么样

```text
scenarios/freight-docs/evals/calibration/
  <caseId>/                 目录名就是用例 id(字母或数字开头,只含字母、数字、-、_)
    session.json            引擎的 SessionState(一局完整的对局)
    human.yaml              人工逐维度打分和理由
    judge-fixtures/1.json   可选:mock 模式下当作"裁判第 1 次的输出"
    judge-fixtures/2.json         ……第 2 次、第 3 次,按文件名的自然顺序
    transcript.md           可选:--init 生成的可读对话,方便标注,不参与计算
```

**session.json** 接受两种形状:命令行 `.sessions/<id>.json` 里的 SessionState 本身,或外面包了一层 `{ "state": … }` 的导出(网页后端存的 `StoredSession`)。场景 id 必须对得上。

**human.yaml** 用严格校验,拼错的键、超过满分的分数、多于一位小数的分数、有分没理由都会直接报错并指出是哪一行:

```yaml
annotator: 你的名字
date: "2026-10-05"
note: 可选,整体印象
dims:
  D1:
    score: 14          # 0 到该维度满分,最多一位小数(15.96 会报错:报告显示成 16,落档却按 15.96 算,两者对不上)
    reason: 见了周总、刘姐、小陈,没去财务;来料分布问到了,损失金额没问到。
  D2: {score: 9, reason: …}
  # …D3 到 D7 一个都不能少
```

`score: null` 表示还没打分(`--init` 生成的模板就是这样)。没填完的用例照样参加稳定性检查,但不参加一致性统计,表格下面会写"跳过:还没填完 D3、D5"。

**judge-fixtures/*.json** 是裁判的原始输出(附录 B 的 JSON),和真模型返回的一样要经过引擎校验:引用不存在的编号、A 级证据没有资料支持,都会按 miss 处理。mock 模式下第 i 份当作第 i 次运行的输出,份数少于 `--runs` 时这个用例算出错。

## 2. 攒 20 份对话

方案要求 20 份:**自己玩 5 份、内测 10 份、脚本化玩家 5 份**。每份用 `--init` 建成一个用例。

**自己玩 5 份(故意玩出好、中、差)**:

```bash
pnpm play                                   # 真模型;需要 .env 里的 Key
pnpm calibrate --init .sessions/s-2026-10-05T08-00-00-000Z.json --id self-01-good
```

好、中、差各至少一份,"中"最有价值:它最容易让人工和裁判出现分歧。`pnpm play --offline` 的对话是模板台词,只适合调规则,不要拿来标定。

**内测用户 10 份**:对局状态整体存在数据库 `sessions.state`(jsonb)里,导出成文件再 `--init`:

```bash
psql "$DATABASE_URL" -At -c "select state from sessions where id = '<对局 id>'" > /tmp/beta-01.json
pnpm calibrate --init /tmp/beta-01.json --id beta-01
```

挑的时候覆盖不同的分数段和不同的玩法(只和老板聊的、资料看得多的、早早报价的……),不要只挑完整玩完的。

**本地网页上玩的对局**(备案之前的 L1 试玩,`pnpm playtest` 或 `pnpm dev:web`,见 [`docs/playtest.md`](./playtest.md)):没有数据库,对局在内存库的落盘文件里(默认 `.data/dev-store.json`)。用 `pnpm session:export` 导出,它按网页后端的同一套约定找库、只读打开:

```bash
pnpm session:export --list                              # 对局 id、轮数、总分、模型调用与花费、脱敏账号
pnpm session:export --id <对局 id> --calibrate beta-01  # 直接建用例(和 --init 是同一段代码)
pnpm session:export --id <对局 id> --out /tmp/beta-01.json   # 或者只导出 { state } 文件,再 --init
```

它和 `pnpm playtest` 一样只读仓库根目录的 `.env`,不读 `apps/web/.env*`;直接用 `pnpm dev:web` 玩、库的变量(`FDE_MEMORY_STORE_FILE`、`FDE_ROOT`、`DATABASE_URL`)写在 `apps/web` 下时,用 `--store-file <dev-store.json>` 指定文件。"模型调用"一列是"无"的是离线模式玩的,不要拿来标定。

有 `DATABASE_URL` 时它读 PostgreSQL(连接设成只读),但要在装好依赖的仓库里跑,`DATABASE_URL` 也要指向这台机器连得上的地址。按 `docs/deploy.md` 部署的服务器上,postgres 不对外开放端口,宿主机的 `.env` 里没有 `DATABASE_URL`(compose 只在 app 容器里拼),镜像里也没有这个工具,所以线上的对局照旧用上面的 `psql`;经 SSH 隧道把容器里的库转到本机再用 `session:export` 读,没有实测【待确认】。

**脚本化玩家 5 份**:

```bash
pnpm calibrate --init-player EV_leading --id script-EV_leading
```

`--init-player` 用离线模式跑 `scenarios/freight-docs/evals/players/` 里的脚本(闸门用脚本里的标准标注,演员用模板台词),完全可复现。对话读起来生硬,但覆盖了"只和老板聊""不停求确认"这些极端走法,适合检查规则的边界。建议从 EV_boss_only、EV_leading、EV_sycophancy、EV_lazy、EV_rude 里挑。

> 仓库里现有的 `example-EV_good`、`example-EV_rush` 就是这样生成的,它们的 human.yaml 是**示例标注,不是作者的真实标注**,只用来演示格式和让 `pnpm calibrate --mock` 有东西可跑。开始正式标定后删掉这两个目录(混在真实用例里时,工具会提醒)。

**标定没过线之前,真实用例放暂存目录** `scenarios/freight-docs/evals/calibration-real/`,上面和第 4 节的命令一律加 `--dir scenarios/freight-docs/evals/calibration-real`(`session:export --calibrate` 同样认 `--dir`)。不直接放进默认目录,是因为:`tools/evals/test/calibrate-run.test.ts` 断言默认目录里正好是那两个示例,多放一份 `pnpm test` 就挂;`pnpm calibrate --mock`(也在 `pnpm ci:local` 里)要求默认目录的每个用例都有至少 3 份 `judge-fixtures`,而且两道门槛都过。两道门槛都过了之后,再把用例挪进默认目录、删掉示例、改那几条测试。

## 3. 先打分,再看裁判

方案 3.4.4 第 2 步:**你不看裁判结果,先给每份逐维度打分并写理由**。顺序不能反,否则标注会被裁判带偏,一致率就没有意义了。

1. `--init` 之后打开用例目录里的 `transcript.md`:事件日志、带编号的对话(U 用户、N 角色、S 旁白)、用户的判断 J1–J5,和裁判看到的是同一份材料。
2. 对照方案 3.4.1 的维度说明,在 `human.yaml` 里逐维度打分,理由写具体:引用编号(U12、J4),写清楚扣在哪。
3. **先把 human.yaml 提交到 git**,再跑裁判。提交记录就是"先标注后看结果"的凭据。
4. 理由里写不出依据的分数,往往就是之后对不上的地方——宁可先空着(`null`)也别猜。

打分时只看这一局本身。D1(事实覆盖)、D3(提问)、D6(承诺)在引擎里是纯规则,D2(证据)也基本是规则;如果你凭感觉给的分和规则算出来的差很多,那正是标定要找的"规则问题"。

### 打分时翻哪些材料

只列位置,不解释规则怎么算分。行号是 `73019e4` 上的,`scenario.yaml` 改过之后要重新核一遍。

标注材料只有用例目录里的 `transcript.md`。同目录的 `session.json` **不是**标注材料(里面有闸门命中的触发器和导演指令),不用打开。

| 要查什么 | 在哪 |
|---|---|
| 事件日志里的 S2、K1 这类编号指哪条事实 | `scenarios/freight-docs/scenario.yaml` 第 116–307 行 `facts:`。每条只看 `statement` 和 `unlock`;`weight`、`key` 两行不用看 |
| 诊断的对照项 | 同一文件第 49–54 行 `truth.diagnosis_items` |
| 资料 | 第 308–364 行 `artifacts:` |
| 验证 | 第 374–400 行 `experiments:` |
| 压力时刻 | 第 401–446 行 `traps:` |
| 判断表单(J1–J5 各是什么) | 第 456–462 行 `judgment_form:` |
| 七个维度各看什么、封顶规则、分数段的含义 | `FDE训练平台-产品与开发方案-v1.md` 3.4.1 节:第 479–484 行、第 486–508 行(跳过第 485 行) |

- D1 凭"关键事实问到了多少"自己判断,不按 `weight` 去算。
- 这页故意没列 `scenario.yaml` 的 `rubric:` 一段。要不要翻它、要不要按 `weight` 算,你自己定;翻过、算过的,在 `human.yaml` 的 `note` 里写一句("看过 rubric""按 weight 算过 D1")。

## 4. 怎么跑

```bash
pnpm calibrate --live                       # 真裁判,每个用例跑 3 次;读仓库根目录 .env
pnpm calibrate --live --record              # 同上,并把裁判输出存成没有 fixture 的用例的 judge-fixtures/1..3.json
pnpm calibrate --mock                       # 不调模型:回放 judge-fixtures
pnpm calibrate --mock --case beta-03 -v     # 只看一个用例;-v 多打印在变的检查项和引擎校验问题
pnpm calibrate --live --runs 5              # 跑 5 次
```

- `--live` 用 `config/models.yaml` 里 judge 环节的模型(经 `@fde/llm` 网关)。缺 Key 时立刻退出并点名缺哪个环境变量(目前是 `DEEPSEEK_API_KEY`)。一局对话的裁判输入大约几千到一两万 token,按 models.yaml 的标价一次几毛钱以内,20 份 × 3 次大约十元以内;跑完会打印实际调用次数和花费。
- `--record` 只写到 `judge-fixtures/` 还没有 json 的用例,不覆盖手写的或之前录的。要重录先手动删掉旧文件。
- 每次运行的明细(含每次裁判的原始输出)写到 `tools/evals/out/calibrate-<模式>-<时间>.json`,和 `pnpm evals` 的输出放在一起(不进 git)。
- 退出码:`0` 两道门槛都过;`1` 有门槛没过,或有用例出错(human.yaml 写错、fixture 份数不够、裁判调用失败,都会打印文件路径和原因);`2` 参数或配置错误(缺 Key、`--init` 的文件不对、`--case` 写了不存在的用例、`--scenario` 的目录或 scenario.yaml 读不进来)。

**mock 和 live 各管什么**:裁判的输出取决于提示词和模型,算分取决于规则。只改了 `scenario.yaml` 的 rubric(规则)时,用 `--mock` 回放录好的裁判输出就能看出规则改动的效果,不花钱;改了裁判提示词或换了裁判模型,必须 `--live` 重跑(再 `--record` 一份新的)。

## 5. 怎么读两张表

以示例标定集为例(`pnpm calibrate --mock`):

```text
一、裁判稳定性:同一对话跑 3 次,总分极差 ≤ 6(±3)为通过

用例             各次总分      极差  在变的维度  结果
───────────────  ────────────  ────  ──────────  ──────
example-EV_good  98 / 98 / 96  2     D4 D7       ✓ 通过
example-EV_rush  4 / 4 / 6     2     D7          ✓ 通过
```

- **各次总分**:每次运行算出的总分(封顶规则之后,和复盘页一样)。
- **极差**:最高减最低,超过 6 就不过。
- **在变的维度**:各次分数不完全相同的维度。通过时也列出来——一直在变的维度是隐患。没过线的用例会在表下面列出具体是哪个检查项在变(比如 `W5:是 / 是 / 否`);通过的用例加 `-v` 也能看到。

```text
二、与人工标注的一致性:各维度满分等分 5 档,相差不超过 1 档算一致;……

用例             D1(20)  D2(15)  D3(15)  D4(20)  D5(10)  D6(10)  D7(10)  一致
───────────────  ──────  ──────  ──────  ──────  ──────  ──────  ──────  ─────
example-EV_good  18|20   13|14   11|15   18|20   9|9     10|10   9|10    7/7
example-EV_rush  1|0     0|0     5|3.8   0|0     4|0 ✗   0|0     1|0     6/7
各维度一致       2/2     2/2     2/2     2/2     1/2     2/2     2/2     13/14

一致 13/14 = 92.9%
```

- **单元格** `人工分|裁判分`。裁判分取 N 次运行里该维度的**中位数**(方案 3.4.2:跑 3 次取中位),一次偶然的抖动不会影响一致性。
- **✗**:相差超过 1 档。
- **各维度一致**:这一列在所有用例里有几个一致。哪个维度的比例低,就先看哪个维度。

表下面的**差异明细**逐条列出 ✗,一条不省;没过线时,每个维度再用"一致但分数不同"里差得最多的用例补满 3 条(✗ 已经有 3 条以上就不补):

```text
  D5 成功定义与干系人:一致 1/2
    ✗ example-EV_rush  人工 4(第 2 档)vs 裁判 0(第 0 档),差 2 档
        人工理由:J3 写了"大会能现场演示",抓住了周总要的一半……
        算分依据:无
        裁判判定:S1 写进、S2 没写、S3 没写、S4 没写、S5 没写
```

三行对照着读:**人工理由**是你当时的判断;**算分依据**是引擎给这个维度加减分的明细;**裁判判定**是裁判对这个维度的检查项(T→D4、S→D5、W→D7)抽出的结论。上面这条:裁判认为 S1 写进了判断,但算分依据是"无"——因为 D5 要求事实**既解锁又写进判断**,这局里 S1 没有通过对话解锁。这是**规则问题**(或标注口径问题),不是裁判抽错了。

最后一行是总结论:`结论:稳定性 ✓ 2/2 · 一致性 ✓ 92.9%(13/14,门槛 80.0%) → 达标`。

## 6. 不达标怎么改

### 稳定性不过

工具会列出这个用例在变的维度和检查项,例如:

```text
✗ beta-04  总分 72 / 64 / 79:总分极差 15 超过 6(±3)
    在变的维度:D4 诊断准确度 15 / 10 / 15;D7 范围与下一步 7 / 5 / 9
    在变的检查项 W3(影响 D7:有可量化的验收指标):是 / 否 / 是
    → 这些检查项写得含糊:把对应检查项改成更具体的是非题(方案 3.4.2 第 6 条),改完重跑
```

- 在变的是 **W 项**(D7):把 `d7_checklist` 里的那一条写成可以逐字核对的是非题。比如"有可量化的验收指标"改成"J4 里至少有一条带数字和对象的验收条件(如'不一致在出货前拦下 90%')"。
- 在变的是 **T 项**(D4,也会带动 D2 的"两条结论有 A 级证据"):看 `truth.diagnosis_items` 的表述是不是一句话里塞了两件事;hit 和 partial 来回跳,通常是"部分命中"的边界没写清楚,在对照项里写明"只说了 X 没说 Y 算 partial"。
- 在变的是 **S 项**(D5):检查"写进判断"的口径,必要时在裁判提示词里加一条例子。
- 检查项的判定是**引擎校验之后**的结果:裁判某次引用了不存在的编号、标了 A 级却没有资料支持,会被降成 miss,看起来也是"在变"。工具会提示"有判定被程序校验降级",加 `-v` 看每次的校验问题;这类问题要在裁判提示词里强调"引用必须是对话里真实存在的编号"。

改完 `--live` 重跑这几个用例(`--case beta-04 --case beta-07`),稳定后再全量跑。

### 一致性不过

按"差异最大的用例"逐条看,先判断是哪一类问题(方案 3.4.4 第 3 步):

| 现象 | 归类 | 改哪里 |
|---|---|---|
| 裁判判定和你的理由一致,但算出来的分不一样 | 规则问题 | `scenario.yaml` 的 rubric:点数、门槛、封顶规则 |
| 裁判判定和你的理由不一致(你认为写到了,裁判判 miss/否) | 抽取问题 | 裁判提示词(`packages/engine/src/judge.ts`)或把对照项、检查项写得更具体 |
| D1、D3、D6 这类纯规则维度普遍对不上 | 规则问题或标注口径问题 | 要么改规则,要么统一你自己的打分标准(写进 human.yaml 的理由里) |
| 只有个别用例对不上,其余都好 | 先复查这份标注 | 你的理由是否引用了具体编号;是不是被这局的整体印象带偏了 |

改规则只需要 `--mock` 回放(裁判输出不变);改了提示词要 `--live` 重跑。**不要为了过线去改人工标注**——除非复查后确认是当初标错了,并在理由里写明改了什么。

### 门槛本身

两个门槛(±3、80%)和档位划分写在 `tools/evals/src/calibration/metrics.ts` 的常量里,来自方案 3.4.2,不要随手调。觉得门槛不合理,先改方案再改代码。

## 7. 之后每次改动都回归

20 份标定用例连同人工标注、录好的裁判输出一起提交到 `scenarios/freight-docs/evals/calibration/`。之后:

- 改了 rubric、引擎的算分或校验 → `pnpm calibrate --mock`(不花钱,几秒钟)。
- 改了裁判提示词、换了裁判模型 → `pnpm calibrate --live`,通过后删掉旧的 judge-fixtures 再 `--live --record` 一份新的,让以后的 `--mock` 回放的是当前裁判的输出。
- 新增标定用例:先 `--init` 再标注,标注提交之后才跑裁判。
