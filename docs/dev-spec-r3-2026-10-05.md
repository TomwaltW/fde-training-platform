### 2.1 各接口的行为规则

**候补名单(F1)**

- `POST /api/waitlist`:`WAITLIST_OPEN=0` 时 403 forbidden「候补名单暂停登记」。`website`(陷阱字段)非空:返回 201 `{ok: true, alreadyJoined: false}`,不入库、不记事件。同一访客(cookie `fde_vid`,没有就按 IP 头 `x-forwarded-for` 第一段,再没有就算一个桶)10 分钟内最多提交 5 次,超了 429。新登记 201 并记事件 `waitlist_joined`(props.source、props.role);已在名单里 200 `alreadyJoined: true`,什么都不改。
- `GET /api/admin/waitlist?status=all|pending|invited`(默认 all):rows 按登记时间从早到晚;`registered` 表示该邮箱已经是用户;`bySource` 里没有来源的记为 `(直接访问)`,按人数从多到少。
- `POST /api/admin/waitlist/invite`:`count` 取最早的 count 个还没邀请的;`emails` 只处理在名单里且还没邀请的(其他的跳过,不报错)。每人 `createInvites(1, 1, "候补:<email>")` → `markWaitlistInvited` → 有 SMTP 就用 `mail.ts` 的 `sendMail` 发邀请邮件,邮件里有邀请码和链接 `<siteUrl()>/login?invite=<码>&email=<邮箱>`(两个参数都要 URL 编码);某一封发失败只把该行 `mailed` 记为 false 并打日志,不中断其他人。
- `GET /api/admin/waitlist.csv`:UTF-8 带 BOM;列:email, role, note, source, created_at, invited_at, invite_code, registered;按 RFC 4180 转义(含逗号、引号、换行的字段加引号,引号写两遍);以 `= + - @` 开头的单元格前面加 `'`,防止 Excel 公式注入;`content-disposition: attachment; filename="waitlist-YYYYMMDD.csv"`。
- 所有 admin 接口用 `requireAdmin`。

**埋点与指标(F2)**

- `POST /api/events`:不需要登录。请求里没有合法的 `fde_vid` cookie 就生成一个并在响应里 `set-cookie`。登录了就记 userId;`sessionId` 只有属于当前用户时才记,否则丢掉这个字段(不报错)。同一访客每分钟最多 60 条,超了照样返回 204 但不入库。成功 204 无响应体。
- `GET /api/admin/gates?since&until`:since/until 是 ISO 时间,省略表示不限。门槛来自 `config/gates.yaml`(F2 新建,文件里写清每个数的来源是方案 6.3,数值照抄方案)。每个指标都给 numerator、denominator、display、status、thresholds、note。计算口径:
  - **第一关** `waitlist_7d`:登记时间在范围内的候补人数。过 ≥100 · 修 30–100 · 不过 <30。
  - **第二关**,对象是开局时间在范围内的对局:
    - `completion` 完成率 = 出了复盘的 / 开局的。过 ≥40% · 修 20–40% · 不过 <20%。
    - `median_minutes` 完成者实际在线时长的中位数:该局的 session_created、turn、action、session_finished 事件按时间排序,相邻两条的间隔累加,每段最多按 `idle_cap_minutes`(默认 10)计;没有事件的老对局不计入样本。过 15–35 · 修 35–50 或 8–15 · 不过 >50 或 <8。
    - `promoters`:完成者中最近一次推荐意愿打 9–10 分的比例(分母是全部完成者,没打分的算不推荐)。过 ≥30% · 修 15–30% · 不过 <15%。
    - `want_next`:完成者中最近一次回答"想玩下一个场景"为是的比例(分母同上)。过 ≥60% · 修 40–60% · 不过 <40%。
    - `share`:完成者中该局有 `share_card_saved` 或 `share_text_copied` 事件的比例。过 ≥15% · 修 5–15% · 不过 <5%。
    - `dispute`:完成者中有申诉的比例。过 <20% · 修 20–40% · 不过 >40%。
  - **第三关** `waitlist_to_paid`:范围内登记的候补里,邮箱对应的用户兑换过任何兑换码的人数 / 范围内登记的候补人数。过 ≥5% · 修 2–5% · 不过 <2%。
  - 分母小于 `min_sample`(默认 10;第一关不设)或值算不出来时 status 为 `insufficient`。
  - `extra.turnLatencyMsP50/P90`:范围内 `turn` 事件的 props.latencyMs。`extra.firstTurnSecondsP50`:范围内有 session_created 的用户,取他最早的 `login` 事件的 visitorId,找该访客最早的 `landing_viewed`,和该用户最早的 `turn` 事件相减(秒);只算两者都有、先后顺序对、间隔小于 24 小时的;`firstTurnSample` 是参与计算的人数。
- 复盘页:推荐意愿那块旁边加一个问题"如果有下一个场景,你想玩吗?"(想 / 不想),提交 `api.feedback(id, {wantNext})`,提交后显示已收到。复盘加载成功后 `track("report_viewed", {sessionId})`。分享卡"保存图片"点击时 `track("share_card_saved", {sessionId})`;新增"复制分享文字"按钮(文字只用 shareCard 的字段 + `location.origin`,不能出现任何真相),复制成功后 `track("share_text_copied", {sessionId})`。

**预售与兑换码(F3)**

- `config/products.yaml`(F3 新建,严格校验,拼错的键直接报错):`free_scenarios`、`human_review_how_to`(Markdown,可为 null)、`products[]`(id、name、price_text、description、includes{scenarios: all 或 id 列表, extra_daily_sessions, human_review}、buy_url、buy_note、available)。仓库里默认放方案 7.1 的「求职冲刺包」和「场景包」两个商品,`available: false`,价格写「【待定】」——上架和定价是作者的决定。
- 配置文件不存在:所有场景免费、没有商品。配置写错:启动时打一次错误日志,按"所有场景免费、没有商品"运行(不能让整站挂掉)。替换 T0 在 `apps/web/lib/server/products.ts` 里的占位实现(`presaleOpen()`:有 available 的商品;`scenarioAccess()`:不在 free_scenarios 里就是 paid)。
- `GET /api/products`:只返回 available 的商品。
- `GET /api/me/entitlements`:来自 `listRedeemCodes({redeemedBy})`;配置里已经没有的商品也列出来(name 用 id,includes 全空)。`dailySessionLimit` = `FDE_DAILY_SESSION_LIMIT` + 各商品 extra_daily_sessions 之和。
- `POST /api/redeem`:需要登录且已同意协议(否则 403 consent_required)。同一用户 1 小时内失败 10 次后 429。码不存在:400 redeem_invalid「兑换码不存在」;已被使用:400 redeem_invalid「这个兑换码已经被使用」。成功记事件 `code_redeemed`(props.productId)。
- `POST /api/sessions`(开局):场景是 paid 且用户没有包含它的权益 → 403 entitlement_required「这个场景需要兑换「<商品名>」后才能玩」(多个商品包含时列第一个上架的)。每日限额改用上面的 dailySessionLimit。
- `POST /api/admin/redeem-codes`:productId 必须在配置里(含未上架的),否则 400。`GET /api/admin/redeem-codes`:`byProduct` 列出配置里的全部商品(含 0 个码的)以及库里出现过、配置里没有的 productId。
- 页面:`/presale`(商品卡片;购买按钮是外链 `buy_url`,新标签页打开,`rel="noopener noreferrer"`;没有 buy_url 就显示 buy_note;"已经有兑换码?去兑换";站内不收款的说明;没有上架商品时显示"预售还没开始"并引到候补名单 `/waitlist`;打开时 `track("presale_viewed")`)。`/redeem`(没登录先去登录再回来;`?code=` 预填)。我的对局页的 `EntitlementsCard`(已兑换的商品、今天能开几局、真人复盘预约方式)。落地页场景卡片:paid 场景显示"需要兑换码",开局遇到 entitlement_required 时给出去预售页的链接。

**手机号登录(F4)**

- 开关:`smsLoginEnabled()`(env.ts)。关着时请求里带 phone → 400 bad_request「暂不支持手机号登录」(T0 现在对 phone 一律这样返回,F4 替换)。
- `request-code`(phone):与邮箱共用 60 秒一次的限频(按规范化后的地址);另有同一手机号每天 `SMS_DAILY_PER_PHONE` 条、全站每小时 `SMS_HOURLY_LIMIT` 条,超了 429(计数在进程内存里,单实例部署够用)。新手机号必须带有效邀请码(手机号没有管理员豁免)。配置了短信就真发;`FDE_DEV_LOGIN_CODES=1` 时在响应里回显 devCode(此时没配短信就不发)。发送失败:退回限频名额,返回 500 internal(日志里不能出现 AccessKey Secret)。
- `verify`(phone):成功后和邮箱一样发 cookie,记 `login` 事件(props.method = "phone")。
- `lib/server/sms.ts`:阿里云 Dysmsapi `SendSms`(RPC 风格,签名方法 HMAC-SHA1、签名版本 1.0,参数按 POP 规则编码:`encodeURIComponent` 后把 `+` `*` `%7E` 换成 `%20` `%2A` `~`),10 秒超时;`Code` 不是 "OK" 就抛错(错误信息带 Code 和 Message)。签名算法要有单元测试(固定时间戳和 nonce,和独立实现算出的结果对比)。
- 日志里的手机号一律用 `maskPhone()` 脱敏。
- 登录页:`site.smsLogin` 为 true 时出现"手机号 / 邮箱"两个入口(默认手机号),否则只有邮箱(和现在一样)。不论哪种,链接里的 `?invite=` 和 `?email=` 预填到对应输入框(候补名单的邀请邮件用)。
- 新增 `docs/sms.md`:开通短信、签名和模板审核、RAM 子账号权限、填哪些环境变量、费用与防刷。

## 6. 测试约定

- 接口测试照 `apps/web/test/helpers.ts` 的写法:直接调用路由函数,`resetForTests()` 重置单例,环境变量在 `beforeEach` 里设、`afterEach` 里还原。
- 需要假的短信服务、SMTP 时在测试里起本地 HTTP 服务或替换 `runtime().mailer`,不要连外网。
- 页面测试一律在 `e2e/mock/` 里用 `MockApi`;断言合规标识(`expectCompliance`)、手机视口不横向滚动(`expectNoHorizontalScroll`)、没有页面报错(`trackPageErrors`)。
- 新页面都要有页脚(复用 `SiteFooter`)和"对话内容由 AI 生成"等现有合规标识,和现有页面风格一致(Tailwind、`lib/client/ui.ts` 的样式常量)。
- 文案用中文,口吻和现有页面一致;不出现"AI 训练营"之类夸张说法。
