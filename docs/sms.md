# 手机号登录:阿里云短信

方案 2.2 的登录是"邀请码 + 手机短信验证码;签名审核通过前用邀请码 + 邮箱验证码"。代码里两种登录并存:

- **没配短信**:登录页只有邮箱,和以前完全一样;接口收到手机号返回 400「暂不支持手机号登录」。
- **配好了短信**(下面四个 `ALIYUN_SMS_*` 都填了):登录页出现"手机号 / 邮箱"两个入口,默认手机号。邮箱登录照常能用,已有的邮箱账号不受影响。
- 手机号账号和邮箱账号是**两个账号**:同一个人先用邮箱、后用手机号登录,会得到两个账号(本轮不做绑定与合并)。

所以签名下来之前什么都不用改;下来以后填好环境变量、重启应用,手机号入口就出现了。

## 1. 开通短信服务

1. 用**公司主体**实名认证的阿里云账号登录控制台,搜索"短信服务",开通(按量付费,开通本身不收费)。
2. 国内短信要求企业资质并做实名制报备,审核约 5–10 个工作日(方案附录 F 的 [S19])。方案 5.2 把它排在 W0 第一天提交,和 ICP 备案并行。

## 2. 申请签名和模板

在短信服务控制台的"国内消息"里:

| 项 | 怎么填 | 备注 |
|---|---|---|
| 资质 | 公司营业执照、经办人信息 | 签名必须和资质主体有关联(公司名、品牌名、已备案网站名) |
| 签名 | 例如 `FDE训练场` | 用途选"自用";适用场景选"验证码"。审核通过后的签名原样填到 `ALIYUN_SMS_SIGN_NAME` |
| 模板 | 类型选"验证码",内容例如:`您的登录验证码是${code},10 分钟内有效。如非本人操作,请忽略本短信。` | 变量名**必须是 `code`**(代码发送的模板参数是 `{"code":"123456"}`),变量属性选"仅数字"。审核通过后把模板 CODE(形如 `SMS_123456789`)填到 `ALIYUN_SMS_TEMPLATE_CODE` |

验证码 10 分钟内有效、同一地址 60 秒只能请求一次,这两个数在代码里写死(`lib/server/login.ts`),模板文案要和它一致。

## 3. RAM 子账号(只给发短信的权限)

**不要用主账号的 AccessKey。**

1. 访问控制(RAM)→ 用户 → 创建用户,勾选"OpenAPI 调用访问",例如叫 `fde-sms`。
2. 创建一条自定义权限策略,只允许 `SendSms`,并限定只能从服务器的公网 IP 调用(把 `203.0.113.10` 换成 ECS 的公网 IP):

   ```json
   {
     "Version": "1",
     "Statement": [
       {
         "Effect": "Allow",
         "Action": ["dysms:SendSms"],
         "Resource": "*",
         "Condition": { "IpAddress": { "acs:SourceIp": ["203.0.113.10"] } }
       }
     ]
   }
   ```

   把这条策略授权给 `fde-sms`。系统策略 `AliyunDysmsFullAccess` 也能用,但它还能改签名、模板、查发送记录,权限偏大。
3. 给 `fde-sms` 创建 AccessKey,ID 和 Secret 分别填到 `ALIYUN_SMS_ACCESS_KEY_ID`、`ALIYUN_SMS_ACCESS_KEY_SECRET`。Secret 只在创建时显示一次。
4. Secret 泄露或人员变动时:在 RAM 里先建新的 AccessKey、换掉 `.env` 重启应用,再禁用并删除旧的。

## 4. 环境变量

都写在服务器上仓库根目录的 `.env`(模板见 `.env.example`),改完执行 `./infra/compose.sh up -d app` 生效(部署见 `docs/deploy.md`)。

| 变量 | 默认 | 填什么 |
|---|---|---|
| `ALIYUN_SMS_ACCESS_KEY_ID` | 无 | 第 3 节的 AccessKey ID |
| `ALIYUN_SMS_ACCESS_KEY_SECRET` | 无 | 第 3 节的 AccessKey Secret |
| `ALIYUN_SMS_SIGN_NAME` | 无 | 审核通过的签名,原样(含中文) |
| `ALIYUN_SMS_TEMPLATE_CODE` | 无 | 审核通过的验证码模板 CODE |
| `ALIYUN_SMS_ENDPOINT` | `https://dysmsapi.aliyuncs.com` | 一般不填;测试里指向本地假服务 |
| `SMS_DAILY_PER_PHONE` | `10` | 同一手机号每个北京时间自然日最多收几条 |
| `SMS_HOURLY_LIMIT` | `100` | 全站每小时最多发几条 |
| `FDE_DEV_SMS_LOGIN` | 关 | **线上不要设**。只在 `FDE_DEV_LOGIN_CODES=1`(开发模式)时有效:不配短信也开放手机号登录,验证码在接口响应里回显,不真发 |

四个 `ALIYUN_SMS_*`(不含 ENDPOINT)少一个都算没配置,登录页不会出现手机号入口。

**上线后自检**:打开 `/api/site`,`smsLogin` 应为 `true`;用自己的手机号走一遍登录(新号码需要邀请码,在管理页生成)。发送失败时接口返回 500「验证码短信没有发出去」,应用日志里有一行 `[auth] 给 138****5678 发验证码短信失败:阿里云短信发送失败:<Code> <Message>`,对照第 6 节排查。

## 5. 费用与防刷

**费用**:国内验证码短信按条计费。2026-05-20 起按量价约 0.042 元/条(月用量 20 万条以内);也可以买套餐包,折合约 0.035 元/条(来源:阿里云《关于国内短信服务价格调整公告》及套餐包页面,以控制台为准)。签名加正文超过 70 个字会拆成多条计费,上面的模板一条以内。按方案的内测规模(每天几十次登录),每月几元到几十元。

短信最大的风险不是正常用量,而是被人用接口给别人的手机号刷短信(花你的钱,还可能被投诉)。代码里的几道闸(都在进程内存里计数,单实例部署够用;多实例部署要换成共享存储):

| 闸 | 数值 | 位置 |
|---|---|---|
| 新手机号必须带有效邀请码,邀请码无效时**不发短信、不计数** | — | `login.ts` |
| 同一地址(邮箱或手机号)60 秒一次 | 固定 | `login.ts` |
| 同一手机号每个北京时间自然日 | `SMS_DAILY_PER_PHONE`(默认 10) | `login.ts` |
| 全站每小时 | `SMS_HOURLY_LIMIT`(默认 100) | `login.ts` |
| 同一 IP 每 10 分钟请求验证码 | 20 次 | `ratelimit.ts` |

几点说明:

- 每天、每小时的条数记的是"发给阿里云的请求",发送失败也算(60 秒的名额会退回)。服务重启后计数清零。
- 超了返回 429,页面上提示用户明天再试或改用邮箱登录。全站每小时的闸被打满时所有人都暂时不能用手机号登录,邮箱不受影响;遇到这种情况先看日志里是不是有人在刷。
- 阿里云自己对验证码短信也有默认流控:同一签名给同一号码每分钟 1 条、每小时 5 条、每天 10 条,超了返回 `isv.BUSINESS_LIMIT_CONTROL`。代码里的每号每天 10 条和它对齐;想放宽要两边一起改。
- 建议在阿里云控制台给账号设余额或用量告警,并且不要给短信充太多钱:即使被刷,损失也有上限。

## 6. 常见错误

阿里云返回的 `Code` 会出现在应用日志里(手机号已脱敏,Secret 不会出现):

| Code | 原因 | 处理 |
|---|---|---|
| `isv.SMS_SIGNATURE_ILLEGAL` | 签名不存在或没审核通过 | 核对 `ALIYUN_SMS_SIGN_NAME` 和控制台里的签名一字不差 |
| `isv.SMS_TEMPLATE_ILLEGAL` | 模板 CODE 不对、没审核通过,或模板和签名不匹配 | 核对 `ALIYUN_SMS_TEMPLATE_CODE` |
| `isv.TEMPLATE_MISSING_PARAMETERS` | 模板里的变量名不是 `code` | 重新申请变量名为 `code` 的模板 |
| `isv.BUSINESS_LIMIT_CONTROL` | 触发阿里云对单个号码的流控 | 正常现象,让用户稍后再试 |
| `isv.MOBILE_NUMBER_ILLEGAL` | 号码不对 | 代码只放行 1[3-9] 开头的 11 位号码,一般不会出现 |
| `isv.AMOUNT_NOT_ENOUGH` | 账户余额不足 | 充值或买套餐包 |
| `InvalidAccessKeyId.NotFound`、`SignatureDoesNotMatch` | AccessKey ID 或 Secret 填错 | 重新复制,注意不要带空格和引号 |
| `isp.RAM_PERMISSION_DENY` | RAM 子账号没有 `dysms:SendSms` 权限,或调用 IP 不在策略里 | 检查第 3 节的策略和服务器公网 IP |
| `TIMEOUT`、`NETWORK` | 10 秒内没响应或连不上 | 检查服务器出网;阿里云偶发故障时用户可以改用邮箱 |

## 7. 实现说明

- `apps/web/lib/server/sms.ts`:直接调用 Dysmsapi `SendSms`(RPC 风格,版本 2017-05-25,`GET` + HMAC-SHA1 签名,签名版本 1.0),不引阿里云 SDK。单元测试(`apps/web/test/sms.test.ts`)用阿里云文档里的两组签名示例和一组独立实现(Python)算出的结果核对签名,并对本地假服务测发送成功、失败、超时。
- 手机号统一存成 `+86` 开头;发给阿里云时去掉 `+86`。日志里的手机号一律是 `138****5678` 的形式。
- 只接了短信服务的 `SendSms`。阿里云"号码认证服务"另有一个面向验证码的接口(`SendSmsVerifyCode`,权限和计费都不同),没有接。

## 8. 合规

- 隐私政策(`apps/web/content/legal/privacy.md`)已经写了"手机号(只在你选择用手机号登录时)"。开放手机号登录前再核对一遍收集范围和第三方(阿里云短信)的说明。
- `docs/compliance-checklist.md` 第 8 项(短信)和最小化收集那一条,在正式开放手机号登录时要同步更新。
